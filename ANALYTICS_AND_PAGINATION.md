# Dewdora analytics and latest products

## Sources and interpretation

The admin `/admin/analytics` dashboard calls `GET /api/v1/admin/affiliate-analytics`. Laravel calculates totals, per-product counts and CTR, per-brand/network counts, placement totals and daily totals from `affiliate_events`. CTR is clicks divided by impressions (zero if no impressions); it is not a unique visitor conversion rate. Products, brands and networks with no matching events still appear with zeroes. This dashboard does not fetch Google Analytics API data and does not use hard-coded totals or affiliate product counters.

The development `DemoAnalyticsSeeder` creates simulated event rows. Its deterministic session namespace is marked `is_demo=true` by the migration, including existing seeded rows. The API defaults to `is_demo=false` for every aggregate and supports `?demo=1` for an explicitly labeled, separate simulated dataset. The admin checkbox shows a prominent demo warning. `DatabaseSeeder` skips all demo data in production. The public popular-products ranking uses real first-party clicks, then impressions, then newest creation time and ID; simulated events do not affect it. A six-hour homepage cache delays changes to ranking until cache invalidation/expiry.

The public frontend observes product card visibility before recording an impression, keeps a per-session product-ID set to prevent duplicate render impressions, and submits `POST /api/v1/public/affiliate-events` for impressions and clicks. Laravel validates the product/session/placement, looks up brand and network, deduplicates impressions by product/session/kind and persists each click to `affiliate_events`. The affiliate link still targets its external offer. Session IDs are browser-generated and are not authenticated identities; blocked browsers, failed requests and ad blockers can lower counts. This is first-party interaction tracking, not page-view or visitor analytics.

GA4 is separate: `frontend/components/analytics/google-analytics.tsx` uses Next `Script` to load one site-wide Google tag; `frontend/lib/analytics.ts` sends `view_item_list`, `select_item`, `view_item`, `affiliate_click` and other product events with product, brand, category, network and placement parameters. Set `NEXT_PUBLIC_GA_ID=G-XXXXXXXXXX` in `frontend/.env.local` and restart/rebuild Next. Without it, the site operates without the GA script. An admin setting for a GA ID is configuration only; it does not fetch or populate admin analytics.

To verify on a real deployment, enable consent where applicable and disable blockers, inspect Network for `https://www.googletagmanager.com/gtag/js?id=G-...` and GA collect requests, then use the GA4 property Realtime or DebugView (with GA debug mode enabled in the browser) while scrolling cards, opening a detail and clicking an offer. In admin Analytics, check first-party totals and product/placement rows independently. Automated browser acceptance verifies Google tag setup and queued events with a test Measurement ID; the CI browser intentionally blocks the external Google domain and cannot prove ingestion by the owner's GA4 property.

## Homepage pagination

`GET /api/v1/public/homepage` sends at most 12 latest active products, newest `created_at` then `id`. After the initial grid, the browser requests the existing `GET /api/v1/public/products?per_page=3&page=5`, followed by pages 6 and 7 as the visitor approaches a sentinel. The archive endpoint uses the same stable backend order, including an ID tie-breaker. The grid stops after 21 products or the backend total and links to `/products` for the entire archive. The popular carousel and hero follow the grid. Inserting new products while a visitor pages through an offset-based list may shift pages; existing IDs are deduplicated in the browser, but snapshot-consistent pagination would require a cursor API.
